# 托管合约与两级推荐返佣

2026-09-17 开发版。代码已实现，本地测试链验证；尚未部署正式托管合约，真实充值、提现仍默认关闭。现有 GitHub Pages 是静态试玩，不能承载数据库、返佣记账或签名服务；本次没有将试玩页面冒充正式后端发布。

## 用户怎么操作

1. 连接钱包并签名登录。好友链接含 `?ref=邀请码`，在首次游戏前展示邀请人地址，确认后绑定；绑定不可更换，不自动绑定陌生人。
2. “我的账户 → 充值”通过钱包授权准确数量，再调用托管合约 `deposit`。后台等至少20个确认，按合约实际收到的币入账。直接 transfer 到合约不计为个人充值。
3. 转盘仍在后台开奖、扣余额、派奖，同时给符合条件的上级返佣。不需要每转一次发链上交易。
4. 完成至少一局后，“我的账户 → 邀请好友”生成链接，可复制分享、查看直推/间推人数、累计奖励和最近50条记录。
5. “提现”先确认金额，后台冻结该笔余额并签发一次性凭证；用户在钱包确认调用合约，款项只能到凭证指定的钱包。成功后点“核对到账”更新记录，运营端也可核对。余额不足、重复使用凭证、篡改金额或收款人均拒绝。

## 返佣口径

| 项目 | 当前实现 |
| --- | --- |
| 直推 | 好友每局下注本金 ×15% |
| 间推 | 下一级好友每局下注本金 ×5% |
| 生效倍率 | 全部倍率，包括0×、0.5×、1× |
| 推荐资格 | 已玩至少一局，且已生成邀请码 |
| 结算时点 | 每局结果和返佣在同一数据库事务提交，自动进入上级可用余额 |
| 无上级/无合格上级 | 对应份额留在奖池，不往其他层补发 |
| 邀请人绑定 | 首次游戏前确认一次；拒绝自推、循环和跨代币关系 |
| 历史账户 | 已玩过的账户不可追溯补绑；历史局不补发新返佣 |
| 测试币 | 不产生真实推荐奖励 |
| 白名单 | 沿用既有专属概率和提现免手续费，返佣比例一致 |

代码配置在 `server/referrals.js` 的 `REFERRAL_RULES`；每局保存政策和实际收款方快照。这里按钱包区分用户，不能证明多个钱包属于不同的人。

当前游戏净返还率77%，销毁仍为下注额9.3%，普通提现当前仍为0手续费。若两级奖励均发放，理论奖池留存 = 100% −77% −15% −5% −9.3% = **−6.3%**；仅直推为−1.3%，没有合格上级为13.7%。返佣从奖池支付，不额外从玩家余额再扣一次。没有擅自调整这几个比例；开启真实资金前需要重新确定能持续的经济参数。

## 资金与销毁

- 用户充值只增加用户余额；运营资金调用 `fundPool` 并核对入账才增加可支配奖池。
- 手续费、返佣、玩家返还、待销毁分别记账；提现不能决定或重算此前的开奖结果。
- 每局计提9.3%为待销毁额度；实际销毁由后台准备批次，合约管理员钱包发送交易。确认上链后才记为已执行。
- 生成销毁凭证前核对账本、链上余额和待完成提现；不得挪用用户可用余额、待领奖励或冻结余额。凭证记录销毁后的最低保留余额。
- 批次待执行期间暂停正式新下注和新提现申请；确认完成或确认过期/撤销后恢复。测试账户不受影响。准备批次前应先清理待完成提现，安排短维护窗口。
- 凭证有效期1小时，以链上区块时间计算。取消钱包弹窗不等于链上取消；必须核实凭证已过期/管理员已撤销，且未执行，才能退回冻结余额或销毁额度。
- `useTokenBurn=true` 调代币 `burn` 并检查 totalSupply 确实减少；`false` 发到黑洞地址并检查实际到账，**黑洞转账不一定减少代币合约的 totalSupply 数字**。部署时明确选择，之后不可更改。
- 充值按实际到账计数；提现和黑洞销毁要求足额到账，转账扣税代币可能回滚。上线前需用最终代币验证，必要时在代币侧配置托管地址免转账税。

## 合约权限

`contracts/SheepGameVault.sol`：固定代币，18位精度，管理员与后台签名人分开。管理员负责暂停、轮换签名人、撤销未执行凭证、注入奖池和执行签名销毁；没有直接提走游戏币的 sweep，也不是代理合约。提现单笔上限与销毁单批上限在构造时固定。

签名包含链ID、合约地址、收款人、数量、凭证ID、过期时间和签名人版本，防止跨合约/跨链/重复使用。服务器持有签名密钥，**此方案仍信任服务器的游戏结算**：签名人被攻破可以签发错误提现，单笔限额不等于总额上限。合约不验证开奖概率或全部玩家余额。本次按正常服务场景实现，不增加服务器永久失联后的自主退出机制。

## 本地运行与验证

需要 Node 22.13+、Foundry（forge/anvil）、Solidity0.8.35、Cancun EVM。

```sh
npm ci
npm run contracts:test
npm test
npm run build
npm run dev
```

`npm test` 先编译合约，后台测试会临时启动本地 Anvil、部署测试币与托管合约、通过实际EVM交易验证充值/提现/销毁，再关闭测试链；不连接真实钱包、不广播主网。

## 正式部署准备

1. 确认最终代币地址、管理员多签地址、后台独立签名地址、单笔提现上限、单批销毁上限，以及 burn/黑洞模式。不要把签名私钥放进部署配置。
2. 使用配置文件准备未签名部署交易，例如：

```json
{
  "token": "最终代币地址",
  "owner": "管理员多签地址",
  "signer": "后台签名公钥地址",
  "maxWithdrawal": "按最终需求填写币数",
  "maxBurn": "按最终需求填写币数",
  "useTokenBurn": false
}
```

```sh
npm run contracts:build
npm run vault:prepare -- deployment-config.json
```

脚本只产出 `artifacts/deployment/unsigned-deployment.json` 和开源验证参数，不签名、不广播。部署到BSC后再以保存的0.8.35编译参数验证源码。先在测试环境以最终代币代码验证资金流程。

3. 后端配置 `PAYMENT_MODE=vault`、`VAULT_ADDRESS`、`TOKEN_ADDRESS`、`VAULT_SIGNER_PRIVATE_KEY`、`BSC_RPC_URL`、`DEPOSIT_START_BLOCK`、`BSC_CONFIRMATIONS=20`、`OPS_AUTH_KEY`。私钥和管理员API密钥仅放服务端secret。先保持 `LIVE_PAYMENTS_ENABLED=false`。
4. 部署Worker和D1迁移0004、0005；确认旧数据备份、账本核对与合约储备一致。旧收款钱包不能通过改配置自动迁移为托管；已有余额需要独立迁移与对账。
5. 确认参数后，在限制外部访问的验收环境启用 `LIVE_PAYMENTS_ENABLED`；管理员调用 `fundPool` 注入奖池，再用下方 `fund TX_HASH` 入账。核对储备、以少量资金验收后，才向玩家开放正式入口。资金接口在开关关闭时不会入账。

## 运营命令

在服务端安全设置 `GAME_API_ORIGIN` 与 `OPS_AUTH_KEY`，不把密钥贴进页面或分享文件。每次有副作用的操作记录 `OPERATION_ID`，网络失败时复用同一个ID重试。

```sh
npm run vault:ops -- audit
npm run vault:ops -- withdrawals
npm run vault:ops -- withdraw-check 提现记录ID
npm run vault:ops -- fund 已确认的fundPool交易哈希
npm run vault:ops -- burns
npm run vault:ops -- burn-prepare 本次销毁币数
npm run vault:ops -- burn-check 销毁批次ID
```

`burn-prepare` 返回交易的 to/data/value；管理员多签审核并发送后，用 `burn-check` 核对。脚本没有管理员私钥、不自动代用户签名，不会擅自循环销毁。当前提供手动批次及对账接口，尚未配置定时任务。
